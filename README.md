# OMS - Order Management System

## 🎯 О проекте

OMS - это система управления заказами с четкой ролевой моделью доступа. Система построена строго по архитектурным диаграммам с использованием ООП принципов.

## 📐 **ВАЖНО: Архитектурные диаграммы**

### ⚠️ **ОБЯЗАТЕЛЬНОЕ ПРАВИЛО:**

**Все изменения в проекте ДОЛЖНЫ соответствовать архитектурным диаграммам в файле `UML_DIAGRAMS.md`**

- 📊 **Диаграммы являются ОСНОВОЙ проекта** - код пишется строго по ним
- 🔄 **При любых изменениях архитектуры** - СНАЧАЛА обновляются диаграммы, ПОТОМ код
- ✅ **Перед разработкой новых функций** - проверить соответствие диаграммам
- 🚫 **Запрещено** изменять код без обновления диаграмм

### 📋 Актуальные диаграммы в `UML_DIAGRAMS.md`:
- **ER-диаграмма** - модель данных и связи между сущностями
- **Диаграмма классов** - ООП архитектура системы
- **Диаграммы последовательности** - бизнес-процессы
- **Диаграмма компонентов** - структура слоев
- **Use Case диаграмма** - функциональность системы
- **Диаграммы прав доступа** - система разрешений

## 🏗️ Принципы архитектуры

### Основная концепция:
```
Администратор → управляет всем
    ├── Создает и настраивает сотрудников
    ├── Дает права (создание заказов, выполнение этапов)
    ├── Создает заказы, типы изделий, этапы
    └── Полный контроль системы

Сотрудник → работает по правам
    ├── Создает заказы (если есть право)
    ├── Выполняет этапы (только назначенные)
    └── Видит только свои заказы

Заказ → проходит через этапы
    ├── Привязан к типу изделия
    ├── Тип изделия определяет последовательность этапов
    └── Сотрудники выполняют этапы по правам
```

### SOLID принципы:
- **S** - Single Responsibility: один класс = одна задача
- **O** - Open/Closed: расширение без изменения базового кода
- **L** - Liskov Substitution: подтипы заменяют базовые типы
- **I** - Interface Segregation: специфичные интерфейсы
- **D** - Dependency Inversion: зависимости от абстракций

### Архитектурные слои:
```
Presentation Layer    → UI компоненты (auth, admin, board)
Application Layer     → Services (User, Order, Process, Admin)
Domain Layer         → Entities (User, Order, Process, ProductType)
Infrastructure Layer → Repositories (LocalStorage)
```

## 👥 Роли и права в системе

### 👑 Администратор (полные права):
- ✅ Создание/редактирование/удаление сотрудников
- ✅ Назначение прав сотрудникам (создание заказов, выполнение этапов)
- ✅ Создание/настройка этапов процессов и типов изделий
- ✅ Создание/редактирование/удаление заказов
- ✅ Просмотр всех заказов и статистики системы
- ✅ Экспорт/импорт данных

### 👤 Сотрудник (права по назначению):
- ⚡ Создание заказов (если дал право администратор)
- ⚡ Выполнение этапов (только назначенных администратором)
- ⚡ Просмотр заказов (только на своих этапах)

## 🔧 Технические решения

- **Frontend:** HTML + CSS + JavaScript (SPA)
- **Backend:** JavaScript (клиентская логика)
- **Хранение:** LocalStorage
- **Авторизация:** Выбор пользователя из списка
- **Архитектура:** Чистая реализация UML диаграмм

## 📝 Правила разработки

### 📊 ОБЯЗАТЕЛЬНО: Трекинг прогресса

**ВСЕ разработчики ОБЯЗАНЫ использовать файл `IMPLEMENTATION_ROADMAP.md` для отслеживания прогресса:**

1. **Перед началом работы:**
   - Откройте `IMPLEMENTATION_ROADMAP.md`
   - Найдите задачу, которую собираетесь выполнять
   - Отметьте её статусом 🚧 (В работе) и укажите своё имя
   - Сделайте коммит с обновлением статуса

2. **После завершения задачи:**
   - Измените статус на ✅ (Готово) и укажите дату
   - Обновите процент выполнения фазы
   - Сделайте коммит с обновлением

3. **При обнаружении проблем:**
   - Добавьте проблему в раздел "Известные проблемы и баги"
   - Используйте соответствующий статус (⚠️ или 🔴)
   - Опишите проблему и возможные пути решения

4. **Проверка прогресса:**
   - Регулярно проверяйте общий прогресс проекта
   - Следите за блокирующими задачами
   - Координируйтесь с другими разработчиками

### ✅ МОЖНО:
- Добавлять новые методы в существующие классы (с обновлением диаграмм)
- Создавать новые value objects (с добавлением в диаграммы)
- Улучшать UI компоненты (не затрагивая бизнес-логику)
- Оптимизировать производительность (не меняя архитектуру)

### ❌ НЕЛЬЗЯ:
- Изменять основные сущности без обновления ER-диаграммы
- Добавлять новые роли без обновления диаграмм прав доступа
- Менять бизнес-процессы без обновления sequence диаграмм
- Нарушать принципы SOLID

### 🔄 Процесс изменений:
1. **Планирование** → анализ текущей архитектуры
2. **Roadmap** → проверка и обновление `IMPLEMENTATION_ROADMAP.md`
3. **Диаграммы** → обновление `UML_DIAGRAMS.md` при необходимости
4. **Код** → реализация по обновленным диаграммам
5. **Прогресс** → обновление статуса в `IMPLEMENTATION_ROADMAP.md`
6. **Тестирование** → проверка соответствия диаграммам
7. **Документация** → обновление README при необходимости
